# Sprint1 后端开发规划：招募与申请

版本：v1.0｜日期：2026-10-26｜状态：待实施  
代码基线：`1d1bb7b`。文件路径均相对项目根目录；HTTP 路径相对后端服务地址，不绑定本机目录、主机或端口。

## 1. 目标与范围

在现有 Django/DRF、PostgreSQL 框架上完成“发布招募 → 浏览筛选 → 提交申请 → 发布者处理 → 申请人查看结果”的后端流程，形成前端首次开发可直接使用的接口、示例和运行说明。

| 范围 | 本次安排 |
| --- | --- |
| 招募 | 标签、列表/搜索/筛选/分页、详情、发布、修改、关闭、删除、我的招募。代码和接口继续使用 `recruitments` 命名。 |
| 申请 | 提交、本人/发布者查询、修改、撤回与重投、接受/拒绝/暂留/取消暂留、状态及人数一致性。 |
| 必要配套 | 私有简历上传/下载、隐私确认、对象权限、站内通知、审计、到期补处理、开发身份、接口文档与回归验证。 |
| 本次不展开 | 完整登录/注册页面及正式认证体系、学校 SSO、真实邮件发送、聊天、个性化推荐、独立项目成员管理、完整管理后台、留存清理平台及正式服务器部署。保留已有预留结构。 |

**权限最新决定：管理员身份不增加申请内容或简历查看权限，也不保留治理查看例外。** 管理员本人若是申请人或发布者，仍按普通业务关系判断；管理员删除违规招募的权限独立处理，不授予正文编辑或简历读取能力。

本次不以初版需求中的量化性能指标为验收门槛，重点保证业务正确、权限明确、事务一致和可复现对接。

## 2. 实现基础与工作基线

已有 10 个业务模型及迁移，公共响应、分页、权限、事务锁、招募状态、简历存储、通知生成和审计工具可复用。HTTP 层目前仅接入账号和健康检查，招募/申请业务服务及接口尚需补齐。现有 173 个测试方法只是源码盘点数量，本次实施前仍须核验运行结果。

主要参考：`backend/design_file/api_before.md`（原始 A 阶段接口约定）、`backend/design_file/api.md`（Sprint1 当前接口契约）、`backend/design_file/design_manuscript/database.md`、`backend/apps/recruitments/`、`backend/apps/applications/`。`backend/tests/contract/test_week1_flow.py` 中的流程辅助函数仅作调用参考，不能视为生产服务已完成。

| 事项 | 本次规划采用的基线 |
| --- | --- |
| 联调身份 | 复用现有 `auth/dev-login` 按编号自动建号并建立会话的能力，满足开发期创建测试身份的需要；暂不新增独立注册/密码体系。保留 `DEBUG` 与 `ALLOW_DEV_LOGIN` 双开关、Session 和 CSRF，不以关闭鉴权替代联调身份。 |
| 状态 | 沿用招募 `open/full/closed` 与软删除；申请 `processing/accepted/rejected/withdrawn/invalid`。暂留为发布者私有标记，申请仍为 `processing`。 |
| 招募约束 | 沿用现有类型、标签、截止时间和人数规则；到期关闭后停止新申请，未满员且关闭未满七天时可处理已有申请。 |
| 申请约束 | 禁止本人投递、重复未撤回投递；仅处理中申请可修改/撤回。撤回后重投生成新记录；接受/拒绝结束普通处理，满员自动拒绝其余处理中申请。 |
| 删除与文件 | 沿用软删除和关联申请失效规则；撤回/失效后按现有策略收紧简历可见性。文件限 PDF/DOC/DOCX、最大 10 MiB，保持私有存储。 |
| 身份能力 | 学生/教师操作范围暂沿用当前实现，以对象关系、权限和状态判断；阶段 1 核对需求与接口字段，出现新决定时记录变更，不自行重设共享模型或权限规则。 |

## 4. 接口交付清单

所有业务路径统一加 `/api/v1`，沿用无末尾斜杠约定。下表为目标清单，不代表已实现；字段和错误行为在阶段 1 的接口文档中确定。

| 交付阶段 | 接口范围 |
| --- | --- |
| 阶段 1：复用并验证 | `GET /auth/csrf`；`POST /auth/dev-login`；`GET /me`；`POST /me/privacy-consent`；`POST /auth/logout`；`GET /healthz`。 |
| 阶段 2：招募 | `GET /tags`；`GET/POST /recruitments`；`GET/PATCH/DELETE /recruitments/{id}`；`POST /recruitments/{id}/close`；`GET /me/recruitments`。 |
| 阶段 3：投递与读取 | `POST/GET /recruitments/{id}/applications`；`GET /me/applications`；`GET /applications/{id}`；`GET /applications/{id}/resume`。申请列表仅发布者可见，详情和文件按关系及状态授权。 |
| 阶段 4：申请变更 | `PATCH /applications/{id}`；`POST /applications/{id}/{action}`，其中 `action` 为 `withdraw/accept/reject/hold/unhold`。未读修改的确认方式一并写入契约并由写服务维护。 |
| 阶段 5：通知 | `GET /notifications`、`GET /notifications/unread-count`；`POST /notifications/{id}/read`、`POST /notifications/read-all`。 |

前端对接文档至少明确：

- 请求方法、必填/可选/只读字段、校验约束、响应示例、空列表、分页、状态及错误码；列表默认每页 20、最大 50，时间使用带时区的 ISO 8601。
- 用户对外使用 `uid`，招募和申请使用资源 `id`；按角色关系裁剪姓名、说明、暂留标记等字段，不返回私有存储路径或多余身份信息。
- Session Cookie 与 CSRF 调用顺序：取令牌 → 开发登录 → 获取登录后的新令牌 → 隐私确认 → 业务写请求。使用配置化服务地址或前端开发代理，不在示例中绑定个人电脑地址。
- 投递使用 `multipart/form-data` 的 `resume`、`note`；浏览器提交时由浏览器生成 boundary。下载成功返回文件流，失败返回约定错误；未命中路由的 404 行为单独说明。
- 页面按钮所需的可操作状态、是否已申请及状态名称应由后端提供或明确映射；前端展示不替代服务端权限复核。

## 5. 实现规范与框架巩固

1. 在 `backend/apps/recruitments/`、`backend/apps/applications/` 补齐 `services.py`、`selectors.py`、`serializers.py`、`views.py`、`urls.py`；文件下载和通知接口放入对应应用，在 `backend/config/urls.py` 集中挂载。按职责分层，避免视图堆积事务与业务规则。
2. 复用 `core` 的响应、错误、分页、时间和权限工具，以及现有 `rules/policies/state`。接口命名和 JSON 字段保持一致，公共函数说明参数、返回、异常及关键约束；只修整本次涉及部分。
3. 新建招募在独立事务中保存招募与标签关系；修改既有招募及其申请时使用 `run_in_recruitment_tx`，不得外包一层大事务。先锁招募、再锁申请并复核；达到人数上限时由 `mark_full` 一并保存人数与满员状态，保证数据库约束成立。
4. 简历先在事务外校验暂存；数据库失败清理新文件，替换成功提交后才清理旧文件。读取文件前复核权限，发布者跨用户读取记审计；管理员无额外读取通道。
5. 数据模型优先复用。确需修改共享模型或迁移时，与相关后端负责人对齐，并同步变更说明及验证；不重写历史迁移或重建已有数据库。
6. 复用现有 `backend/tests/` 并补充本次功能的必要验证，覆盖正常流程、权限拒绝、状态边界及事务回滚；交接文档提供可独立复现的步骤和脱敏示例。
