## 1. 目标与范围

以 `file/tasks/软件需求规格说明2.0修订稿.md`、本计划明确的补充约定及现有代码为依据，完成以下后端交付：

- 支持普通账号注册登录及管理员权限判定，为公告管理和业务联调提供真实的应用账号入口。
- 完成公告列表、详情、发布、编辑、本人删除和管理员治理删除，支持首页公告展示与招聘页切换。
- 复用既有招聘、申请、PDF/DOC/DOCX 上传及站内通知能力，完成 200 人上限、删除人数归零、长期记录访问、治理权限等规则适配。
- 走通公告到招聘、申请处理、通知及个人申请状态的完整流程，提供准确的接口契约、回归结果和交接记录。

### 1.1 本轮补充约定

| 事项 | 本轮执行口径 |
| --- | --- |
| 注册与登录 | 使用 `@tongji.edu.cn` 邮箱和自设密码注册，后续凭邮箱、密码登录；校验邮箱格式及完整域名，不发送认证邮件或验证码。 |
| 认证能力边界 | 邮箱后缀只作为注册准入条件，不表示已验证邮箱归属或师生实名身份。现行需求稿已统一为邮箱密码注册登录；阶段 1 细化接口说明与认证参数。 |
| 简历访问 | 申请撤回或招聘删除后，申请人仍可下载自己提交且仍保存的简历；发布者失去对应简历访问权限。管理员不因治理权限获得他人简历访问权。 |
| 公告权限撤销 | 公告作者失去管理员权限后，不再允许发布、编辑、本人删除或治理删除公告；旧公告由现任管理员按治理规则处置。 |
| 留存与通知 | 不按固定 180 天期限清理或隐藏合法历史申请、简历和通知；仍执行状态及对象关系权限。业务事件只生成站内通知，本轮不发送任何业务或认证邮件。 |

除上述已明确调整外，按 2.0 修订稿执行。聊天、推荐、完整管理后台、密码找回邮件、学校 SSO 接入、生产部署验收及容量驱动的归档清理不纳入本轮。初版量化性能指标不作为本轮硬性门槛；前端页面实现由前端负责，后端提供接口及联调支持。

## 2. 核心业务与工程约束

### 2.1 账号与权限

- 注册邮箱去除首尾空白并统一大小写，域名须精确等于 `tongji.edu.cn`；不得接受相似域名、额外后缀或客户端指定的管理员标记。
- 复用 Django 密码验证器、哈希和会话机制，不自建密码存储格式。注册成功建立会话，登录和注册均轮换必要的会话/CSRF 凭据；匿名请求同样执行 CSRF 校验。
- 登录失败统一处理不存在邮箱、错误或不可用密码；有效凭据命中停用账号时拒绝。注册、登录实施可验证的失败限流，具体阈值及并发一致的计数方式在阶段 1 固定。
- 注册不得覆盖已有账号的密码、身份绑定或权限；大小写相同邮箱及并发重复注册只允许一个账号。历史开发账号若无可用密码，通过受控管理方式初始化，不提供“仅凭邮箱重新设置密码”的公开入口。
- 新注册账号为普通用户，不赋予 `is_admin`、`is_staff` 或超级用户权限。内部兼容标识由服务端生成；姓名、师生标签仅作未核验的展示信息，不从邮箱前缀推导授权。
- 管理员授予/撤销使用受控管理命令；业务权限仍依据 `is_admin`，不混同 Django Admin 登录权限。撤销后既有会话的后续管理员操作也须被拒绝；本人招聘与申请仍适用普通用户权限。
- 保留开发登录供隔离联调，正式注册登录验收不能用开发登录替代；非开发配置禁用开发身份入口。测试专用密码哈希配置不得用于正常服务进程。

### 2.2 公告

- 公告查询要求登录，只返回未删除记录，按 `created_at DESC, id DESC` 稳定分页。保留现有 `is_pinned` 字段，但本轮 HTTP 不提供置顶能力，也不按置顶排序。
- 提供标题、纯文本正文、`time_kind`、`event_at`、可选报名链接与关联招聘。时间须为带时区的合法值；链接仅允许 HTTP/HTTPS 绝对地址。已过活动时间不自动等于已删除，编辑正文不因历史时间被一并拒绝。
- 发布要求当前管理员权限；编辑及本人删除同时要求当前管理员权限和作者身份。其他管理员只能治理删除，不得修改他人公告。
- 治理删除要求非空原因，并在同一业务事务中完成软删除、审计及发布者站内通知；正常发布、编辑和本人删除不广播公告通知。
- 写操作在锁内重新读取对象并校验状态和权限。重复删除返回明确的不存在/已删除结果，不能重复写删除事件或通知；更新与删除竞争不能使公告恢复可用。

### 2.3 招聘、申请与简历

- `max_headcount` 为正整数且不超过 200；已有 `min_headcount` 可空，提供时满足 `1 <= min_headcount <= max_headcount`。所有容量判断使用上界，不以申请记录总数代替招募人数。
- 发布及编辑的截止时间须晚于提交时的服务器时间且不超过一个日历年；本人编辑、关闭及删除保持进行中、未删除等状态限制。满员与截止同时发生时按满员处理。
- 关闭后的处理期限为 `closed_at + 7×24 小时`，仅严格早于期限终点时可处理既有申请；满员和期限届满分别自动拒绝剩余处理中申请。执行时复核状态，不能只依赖页面或定时任务。
- 本人删除与管理员治理删除使用不同入口。普通删除按发布者身份和招聘状态校验，即使发布者拥有管理员标记也不自动绕过限制；治理入口要求管理员权限及原因，可处置任意未删除状态的招聘。
- 删除在同一事务内完成 `processing/accepted → invalid`、`accepted_count=0`、删除标记、访问撤销、通知和审计；`rejected/withdrawn` 不变。保留招聘业务状态及历史时间，不因人数归零重新开放。
- 增加结构化的申请状态变更追溯，至少包含关联对象、前后状态、事件原因、操作者或系统来源和发生时间；覆盖接受/拒绝、撤回、自动拒绝及删除失效。历史处理结果不能仅靠累计人数或通知文案推断。
- 核对并修复历史已删除招聘的统计值；旧记录无法可靠还原的状态历史明确标注证据边界，不编造历史事件。
- 申请修改、撤回、暂留、处理和已阅继续遵守状态与时间窗口；撤回重投生成新记录，暂留不改变 processing 状态，也不通知申请人。并发采用既有招聘锁、申请锁顺序，避免超员或重新接受已失效申请。
- 简历保持非空 PDF/DOC/DOCX、最大 10 MiB 的既有契约；上传失败无残缺申请，替换成功清理旧版文件。撤回或删除不删除仍需留存的简历；本人可读取自己的保留文件。申请撤回后发布者禁读对应简历，招聘删除后发布者禁读其下全部简历，不以申请是否转为 invalid 作为唯一判断；无关用户及管理员无额外访问权。

### 2.4 长期记录与站内通知

- 移除申请查询、详情/简历权限、通知生成和通知查询中的固定 180 天截断；保留七天处理窗口、归属校验、删除提示及敏感字段裁剪，不提供借历史记录恢复公开详情或绕过权限的通道。
- 业务通知只在成功事务中创建，重复处理同一事件不得重复生成。移除新增业务 `EmailLog(PENDING)` 及邮件派发回调；保留旧表和历史数据，不进行无关删除。
- `email_notify_enabled` 暂作兼容字段保留，不控制任何发信行为，新前端不将其展示为可用邮件通知功能；具体兼容行为写入 API 正文。
- 公告治理通知提供公告标识、名称、处置结果和原因；采用可空公告关联扩展现有通知模型/响应，与招聘/申请关联语义分开，旧通知保持兼容。已删除目标仍可展示通知及删除提示，不恢复目标公开详情。
- 招聘治理通知必须包含原因，不能仅在审计中保留。阶段 5 按下列矩阵验证接收人与去重。

| 事件 | 接收人及要求 |
| --- | --- |
| 提交、修改、撤回申请 | 招聘发布者；修改后保留未读修改标记，直到有效的已阅确认。 |
| 接受、主动拒绝、满员自动拒绝、关闭超时拒绝 | 相应申请人；拒绝通知区分原因。 |
| 修改招聘 | 修改前仍为 processing/accepted 的申请人；修改引起的自动拒绝作为另一个事件通知。 |
| 删除招聘导致失效 | 本次转为 invalid 的申请人；治理删除另向招聘发布者通知处置结果及原因。 |
| 治理删除公告 | 公告发布者；包含内容名称、处置结果、原因和正确的目标引用。 |
| 暂留/取消暂留、正常发布或编辑公告 | 不生成申请状态通知或公告广播通知。 |

## 3. 分阶段实施与交付

阶段按依赖推进；每阶段以实际提交和验证结果交付，不以计划中的“拟实现”内容代替已完成能力。

### 阶段 1：基线、需求与契约统一（zf 主导，czh 参与）

**工作内容**

1. 核对共享分支与运行文件版本，在独立测试数据库应用既有迁移，完成系统检查、迁移差异检查和当前全量回归，记录真实结果。
2. 核对需求稿与本计划的注册登录、本人简历读取及管理员撤权约定，细化对应验收用例；补齐或落实需求稿标明待补充的《需求验收测试用例》《修订说明与待确认事项》，不把缺失附件当作已确认规则。
3. 在 `backend/design_file/api.md` 建立本轮契约，区分已实现与待实现；明确注册登录字段/错误码、身份展示、删除入口、权限输出、通知扩展、历史记录及兼容策略。
4. 固定密码验证、失败限流、公告字段长度、标签与文本校验等工程参数；未由需求指定的参数明确记录为设计决策，避免两人分别设定。
5. 明确公告通知关联、申请状态追溯及历史人数修复的数据方案、迁移归属和验证方法；与现有数据库设计对齐。zf 负责公告通知底座和停止业务邮件任务，czh 接续实现招聘/申请规则及长期通知适配。

**通过条件：** 当前基线可复现，失败项有结论；跨模块契约和数据变更方案可直接用于实施，原需求与本轮补充约定不再相互矛盾。形成 `Record/stage_01_baseline.md`。

### 阶段 2：邮箱密码注册登录与管理员配置（zf）

**工作内容**

- 完成重复注册、并发建号、错误凭据、停用账号、限流和匿名 CSRF 校验；注册不能改写已有账号，错误路径不泄露密码或敏感资料。

- 更新账号接口文档与共享回归；注册/登录只返回必要本人资料，不返回密码摘要或内部认证标识。

**通过条件：** 可通过真实 HTTP 完成“获取 CSRF → 注册普通账号 → 退出 → 邮箱密码登录 → 读取本人资料”；管理员配置和撤销可验证，旧会话不能继续行使已撤销权限，账号回归及相关全量回归通过。形成 `Record/stage_02_auth.md`。

### 阶段 6：联合验收与最终交付（czh 主导，zf 复核）

**工作内容**

## 4. 接口与数据变更边界

HTTP 统一使用 `/api/v1` 前缀、不带末尾斜杠，以下省略统一前缀。字段及完整错误码集中维护在 `backend/design_file/api.md`。

| 方法与路径 | 权限及用途 | 计划阶段 |
| --- | --- | --- |
| `POST /auth/register` | 公开但强制 CSRF；邮箱密码注册，成功 201 并建立会话 | 2 |
| `POST /auth/login` | 公开但强制 CSRF；邮箱密码登录，成功 200 | 2 |
| `GET /announcements` | 已登录；未删除公告列表，按发布时间稳定倒序 | 3 |
| `GET /announcements/{id}` | 已登录；详情及当前权限，已删除/不存在返回 404 | 3 |
| `POST /announcements` | 当前管理员；发布公告，成功 201 | 3 |
| `PATCH /announcements/{id}` | 当前管理员且为作者；部分更新 | 3 |
| `DELETE /announcements/{id}` | 当前管理员且为作者；本人软删除 | 3 |
| `DELETE /admin/announcements/{id}` | 当前管理员；治理删除，原因必填并通知作者 | 3 |
| `DELETE /admin/recruitments/{id}` | 当前管理员；治理删除任意未删除状态的招聘，原因必填 | 4 |

同时调整既有 `DELETE /recruitments/{id}` 为本人删除语义；账号、通知、个人申请及简历接口按新规则适配。现有权限输出须区分本人删除与治理删除，前端使用不同操作入口。`/auth/csrf`、`/auth/logout`、`/me`、隐私确认及已有业务接口继续复用；SSO 保留为未接入状态。

计划新增 9 个方法/路径，全部交付后累计 40 个已实现方法/路径，另有 2 个 SSO 预留；统计包含受开发开关控制的原有开发登录。数量不代替功能验收。

**数据与兼容要求：**

- 复用现有用户、密码、公告及业务模型；不新增邮件验证码模型或 SMTP 配置要求。
- 为公告治理通知增加可空关联，并完善目标关联的互斥/一致性校验、查询与响应；保留旧通知数据及字段的兼容性。
- 为申请状态历史及删除后人数语义提供必要的新迁移/数据修复，记录依据、范围和验证方法；未知历史明确标记，不擅自重置数据库。
- 允许为确认的新需求修改服务、权限、查询、契约和测试；不重写历史迁移，不因改动方便而进行无关重构、删除旧数据或移除未评审字段。

## 5. 验收矩阵

| 范围 | 必须覆盖的结果 |
| --- | --- |
| 注册与登录 | 精确域名、大小写重复、并发注册、弱密码与非法字段、错误/不可用密码、停用账号、CSRF、限流、会话退出及轮换；不能覆盖已有账号或自行授予管理权限。 |
| 管理员撤权 | 原管理员的后续公告发布、编辑、本人删除及治理删除请求均被拒绝；旧会话不能绕过。仍保留普通用户的招聘、申请和本人数据访问能力。 |
| 公告 | 列表/详情/创建/修改/删除；发布时间并列时稳定排序；过去时间公告与正文编辑；非法链接/关联招聘；集合 PATCH/DELETE 为 405，对象越权为 403，已删除为 404。 |
| 公告治理 | 原因必填、作者通知及审计正确；重复删除及更新/删除竞争无重复副作用、无恢复；本人删除不误走治理。 |
| 人数与删除 | 200 成功、201/非正数/错误类型拒绝；区间下界与上界关系正确；删除后人数为零，原处理结果可追溯，历史数据适配有证据，重复补执行不重开。 |
| 状态与并发 | 截止停止投递、满员优先、七天处理边界、撤回重投、暂留及已阅版本；最后名额、接受/撤回、删除/处理竞争不超员、不接受已失效申请。 |
| 文件与权限 | PDF/DOC/DOCX、非空、10 MiB 边界、伪造文件、上传/替换失败清理；本人可下载保留简历。申请撤回后发布者禁读对应简历；招聘删除后，其下全部申请的简历对发布者禁读，包括状态保持 rejected 的记录；无关用户和管理员无额外访问权。 |
| 长期记录与通知 | 179/180/181 天及更长期的授权记录不被固定期限隐藏；通知生成、列表、未读数、已读范围一致；业务新邮件任务为零；通知和审计与业务事务一致。 |
| 联调 | 普通注册登录贯穿公告、招聘、申请、通知与个人状态；HTTP 与浏览器验收分别记录，删除提示及两种管理入口与后端权限一致。 |

错误码按实际前置状态及冻结后的 API 契约断言。例如，满员自动拒绝后的申请已不再 processing，不能仅因招聘已满员而强行要求返回 `RECRUITMENT_FULL`。查询键重复、JSON 字段和 multipart 多值分别验证，不把已有查询校验表述为通用 JSON 重复键检测。

在确认独立测试库及环境配置后，于 `backend/` 执行：

```bash
python manage.py check --settings=config.settings.test
python manage.py makemigrations --check --dry-run --settings=config.settings.test
python manage.py test tests --keepdb --noinput --settings=config.settings.test
```

另以正常开发设置执行真实 HTTP 主流程，并运行 `git diff --check`。记录实际通过、失败、跳过及原因；旧断言因需求改变而调整时记录对应规则，不能通过跳过用例掩盖缺陷。测试仅用合成身份、测试密码和虚构简历，日志与交付材料不包含真实凭据或个人资料。
